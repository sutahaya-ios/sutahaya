# HayaosiApp Codexワークストリーム

最終整理日: 2026-09-05

巨大な単一Codexスレッドを終了し、以下の5領域を独立して運用する。各スレッドは自領域の情報だけを基本とし、領域横断の判断は00へ戻す。

## 現在の担当体制

- トキヤ: 01 対戦タブUI
- トキヤ: 02 Firebase
- トキヤ: 03 Security
- トキヤ: 04 Debug / 実機検証
- 00 Architecture: ユーザーとプロジェクト全体の司令塔。担当間の前提調整を行う

過去の担当分担と衝突する場合、この担当体制を優先する。

## 00｜Architecture / 司令塔

### 責務

- 全体設計と仕様判断
- タスク分解と優先順位
- 複数領域へまたがる変更の調整
- 古い仕様と現在仕様の衝突解消
- リリース前の残件整理
- Bundle ID、Signing、XcodeGen等の共有前提管理

### 最初に読む情報

- `PROJECT_CONTEXT.md`
- `DECISIONS.md`
- `WORKSTREAMS.md`
- 必要な場合だけSTATUSの該当部分

### 変更してはいけないこと

- 専門領域の前提を担当スレッドへ確認せず変更しない
- 本番Bundle ID、Signing、Teamを独断で変更しない
- 旧要件へ現行実装を無理に戻さない

### 現在の主なタスク

- 3台実機検証後のリリース判断
- App Store Connect残件の整理
- Cloud Functions、App Check、ルーム削除等のバージョン割り当て
- STATUSと正式引き継ぎ文書の整合

### 他領域への依存

- 対戦仕様: 01
- バックエンド構造: 02
- 認証認可: 03
- 未再現・実機結果: 04

## 01｜Battle UI

### 担当

トキヤ

### 責務

- SwiftUIの対戦タブ
- 対戦ホーム、ルーム作成・参加導線
- 待機ロビー、対戦画面、リザルト
- クライアント側の回答状態とUX
- 初回チュートリアル
- CPU対戦とオンライン対戦の共通表示

### 現在仕様

- ホームからルーム作成、コード参加、CPU対戦、招待参加を直接行う
- 前回設定をローカル保存する
- 文字送り＋選択肢タップ回答
- 対戦中は下部タブを隠す
- PvPリザルトでは復習ボタンを出さず、履歴保存だけ維持する
- Presenceや見た目だけのFirebase機能を追加しない

### 制約

- Firebaseデータ構造やRulesをUI都合で独断変更しない
- 対戦ルール数値をViewへ複製しない
- CPU対戦を通信修正で壊さない
- 既存の3タブ構成を維持する

### 再発防止ルール

- 重要なFirebase状態は、画面内だけの一時的な`Set`や`Bool`を唯一の正として管理しない。サーバー状態とローカル表示状態の役割を明確に分ける
- 複数段階の処理失敗を、内部的にすべて同じ「エラー」へ潰さない。ユーザー向け表示は簡潔でも、Debug時に処理段階・error code・元errorを識別できる情報を残す
- UI上で成功したように見えることを、バックエンド処理完了の証拠にしない。サーバー側の完了結果を確認して成功として扱う
- 関連する基本happy pathが実機で通るまでは、周辺UI改善へ作業範囲を広げない

### 未完了・既知問題

- 3台でのロビー・複数問表示確認
- 一時切断復旧時の表示確認
- 日本語IMEの自己紹介入力問題は対戦UI外のため04で切り分ける

### 完了条件

- 指定された対象画面のdiff確認
- リスクに応じた最小表示確認
- 通信固有部分は02・04の結果を受ける

## 02｜Firebase

### 担当

トキヤ

### 責務

- Firebase初期化と匿名Auth
- Firestoreのプロフィール、フレンド、申請、招待
- RTDBのルーム、同期、対戦状態
- データモデルとクライアント通信
- 本番・開発用Firebase iOS Appの共存

### 現在仕様

- 同じFirebase Project `hayaosiapp`を複数Bundle IDで共有
- FirestoreとRTDBを役割分離
- v1.0はホスト権威
- 回答はquestionIndex、choice、ts、visibleCountを持つ
- failedはquestionIndexへ紐付く
- ルーム招待はCloud FunctionsでRTDB上のhostを検証して作成する

### 制約

- plistをGit管理しない
- 開発用plistで本番設定を上書きしない
- データ構造変更時は03とRulesテストを整合させる
- CPU対戦へFirebase依存を入れない

### 未完了・既知問題

- 採点のCloud Functions化は未導入
- 使用済みルーム自動削除なし
- 満員判定の競合余地
- `onDisconnect`による一時切断誤判定
- セットアップ文書のデータ図が古い可能性

### 完了条件

- 正常系と失敗系の通信経路を確認
- Rules変更がある場合は03と連携
- 実機固有同期は04へ引き渡す

## 03｜Security

### 担当

トキヤ

### 責務

- Firestore / RTDB Security Rules
- 認証・認可
- 入力schema検証
- 不正回答・不正得点対策
- App Check検討
- 本番公開前のSecurityレビュー

### 現在仕様

- ホストだけが進行・問題・得点を更新
- waiting中だけ参加者が自分を追加
- 参加者は自分の現在問題の回答だけを書ける
- Firestoreは所有者、相互申請、フレンド関係を検証
- 全件列挙を基本的に許可しない

### 制約

- ゲームルール自体をSecurity担当が独自変更しない
- 暫定的な全面read/writeへ戻さない
- Consoleだけを編集してGit上のRulesと分離させない
- 正常ユーザーの通信を拒否しないことも検証する
- 本番公開前に影響と未検証事項を説明する

### 未完了・既知問題

- App Checkの導入判断
- クライアントへ正解が配信されるため完全な不正防止ではない
- room code総当たりや匿名認証悪用への追加対策
- 過去に古いRules公開でオンライン全体が停止した

### 完了条件

- Rules Emulatorの関連ケース
- 実際のクライアントpayloadとの一致
- 本番公開は明示的な許可後
- 公開後の実機正常系は04で確認

## 04｜Debug

### 担当

トキヤ

### 責務

- 原因不明バグ
- クラッシュ、Buildエラー
- 再現条件と影響範囲の特定
- 実機2台・3台検証
- 通信遅延、切断、状態競合
- 修正後の回帰確認

### 既知の重要な再現履歴

- 2問目以降、一方だけ回答不能になる
- 相手が回答するまで回答権が復活しない
- 同時誤答で別プレイヤーがお手付きになる
- 実機とSimulatorで問題進行がずれる
- 同時押しを繰り返すとホスト退出扱いになる
- 古いFirebase Rules公開でオンライン全体が停止する
- XcodeGen再生成不足で新規型が見つからないBuildエラーになる

### 制約

- 原因がない領域を同時に変更しない
- UI、Rules、データ構造を一度に広範囲変更しない
- Build成功を実機バグ解決と扱わない
- 未コミット差分を勝手に破棄しない

### 最優先の未完了検証

1. 双方が3問連続で相手を待たずに回答できる
2. 誤答状態が次問へ残らない
3. 同時押しを繰り返してもホスト退出扱いにならない
4. 本当にホストが切断した場合だけルームが終了する
5. 3人・3台で同じ進行と得点になる

### 完了条件

- 再現手順、期待結果、実際の結果を記録
- Simulator確認と実機確認を区別
- 未検証事項を明記
- 原因が他領域なら担当スレッドへ最小限の証拠を渡す

## 領域横断ルール

- UI変更がFirebase schemaを必要とする場合: 01 → 02 → 03
- Firebase変更がRulesへ影響する場合: 02と03を同じ判断単位にする
- 実機でのみ発生する問題: 04が再現条件を整理し、原因領域へ渡す
- ゲーム仕様の変更が必要な場合: 00で決定してから01〜03へ展開する
- Bundle ID、Signing、`project.yml`、新規依存: 00で影響確認する

### 大きな機能の設計・完了ルール

- 設計の最初に、ユーザーが入口から目的達成まで操作として最後まで通せる、最小のhappy pathを1本定義する
- 完了条件は次の4段階へ分け、それぞれの状態と未確認事項を記録する
  1. 実装: 必要なクライアント、データ構造、Rules等が実装されている
  2. 自動テスト: 対象ロジック、payload、Rules等の必要なテストが成功している
  3. deploy: Firebase Rulesやバックエンド等、共有環境への反映が必要なものが実際に反映されている
  4. 実機E2E: 実際のユーザー操作でhappy pathを入口から結果まで通して確認できている
- happy pathが成立する前は、その成立を妨げる問題への対処を優先し、追加のrace対策、Security hardening、将来拡張を過剰に積まない。必須でない強化は後続タスクへ分ける
- Firestore、RTDB等の複数サービスを跨ぐ処理は、設計時点でpartial success、retry、idempotency、stale operationを確認し、中断後の状態、再試行時の重複防止、古い操作の無効化方法を決める
- 元Issueの症状を同じ条件で再確認できていない場合は「解決済み」としない。「修正実装済み・元症状未確認」等、実装状態と再現確認状態を分けて記録する

## 各新スレッドの初回メッセージに含めるもの

- 担当領域と変更禁止範囲
- この文書の該当セクション
- `PROJECT_CONTEXT.md`の共通制約
- `DECISIONS.md`の関連判断
- STATUSの該当タスクだけ
- 実機未検証か、確認済みか

新スレッドは巨大旧スレッドの再読を前提にしない。判断に必要な情報が文書に無ければ、推測せず00へ「要確認」として戻す。
