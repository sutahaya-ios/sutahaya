# 作問機能 MVP

## 対応範囲

- ○×・4択・短い記述を1つの問題集へ混在できる。問題集は1〜20問、短文の正解候補は1〜5個。
- 問題集タイトル、問題文、正解、任意の解説を手動入力し、保存後は編集しない。
- 自作問題集とフレンドから追加した問題集を同じライブラリに表示する。
- 全体公開・検索、AI作問、一人用プレイ、作問問題での対戦は今回の対象外。
- 既存のSwiftData schema・Competitive・Realtime Databaseの処理は変更しない。

## Firestore構造と処理

| パス | 内容 |
|---|---|
| `questionSets/{setID}` | `title`、`creatorUID`、`createdAt`、`questions`、`status`、`schemaVersion`。問題集IDはdocument IDを使用 |
| `users/{uid}/library/{setID}` | `questionSetID`、`addedAt`。本文を複製せず元の問題集を参照 |
| `users/{uid}/sharedQuestionSets/{setID}` | `questionSetID`、`fromUID`、`toUID`、`fromNickname`、`title`、`sentAt`。共有受信一覧 |

`QuestionSetService`が既存の認証・フレンド情報を利用する。各書き込みはFirestore transaction（読み取り結果に基づく変更をまとめて確定する処理）で行い、日時はserver timestampを保存する。

1. **作成**: Swiftで全問を検証 → 問題集・作者のライブラリ参照を読む → 両方を同じtransactionで作成する。片方だけの保存を許可しない。
2. **共有**: 問題集・相手の既存受信項目・作者プロフィールを読む → 作者かつ利用可能な問題集であることを確認 → 相手の受信項目を作成する。Rulesでも相互フレンド関係と作者を検証する。
3. **追加**: 問題集・自分の受信項目・既存ライブラリ参照を読む → 利用可能状態と送信者を確認 → 自分のライブラリ参照を作成する。受信項目は残す。

同じ下書きの保存再試行には固定した`draft.id`を使う。共有・ライブラリのdocument IDも`setID`に固定し、既存項目があれば再作成しない。保存済みの同一IDへ異なる本文を送ることは拒否する。

読み込みはserverを明示し、書き込みの成功応答後に画面へ反映する。読めない形式の問題集・共有は該当項目だけを除外して警告し、正常な問題集を表示する。

## 権限・状態

- 状態は`active`・`blocked`・`deleted`。作者が行える状態変更は`active → deleted`のみ。`blocked`は将来の管理対応用で、管理画面・復元操作は用意しない。
- 共有できるのは作者のみ。受信者から第三者への再共有はできない。
- 共有後にフレンド関係を解除しても既存の受信項目・ライブラリ参照は維持する。問題集が`active`なら既存共有からの追加・閲覧も継続できる。
- 削除は論理削除。再読み込み後、全利用者のライブラリと問題本文を非表示にし、受信一覧では「利用できません」と表示する。元データや参照は物理削除しない。
- Rulesは権限、タイトル等のmetadata、1〜20問の件数、各問題がmapであること・対応形式・問題文が文字列であることを検証する。詳細な型、文字数、選択肢・正解の整合性、重複はSwiftの`validated()`で保存時と読み込み時に全件検証する。Rulesの式数上限に収めるため、本文の詳細検査はRulesへ重複実装しない。

## 2ユーザーでの通し確認

事前に、検証先へ作問Rulesが適用されていることと、別々のユーザーA・Bが相互フレンドであることを確認する。

1. Aで作問タブ → 新規作成 → ○×・4択・短文を1問ずつ登録 → 3問の問題集を保存する。
2. Aのライブラリで内容を開き、アプリを再起動して同じ問題集・3問が残ることを確認する。
3. Aで問題集詳細 → フレンドに共有 → Bを選択して共有する。
4. Bで作問タブを更新し、送信者・問題集名を確認 → 「ライブラリに追加」 → 3問の内容を確認する。
5. Bのアプリを再起動し、ライブラリと内容が残ることを確認する。同じ共有の再送・追加で件数が増えないことも確認する。
